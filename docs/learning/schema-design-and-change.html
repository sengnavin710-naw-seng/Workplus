Workforce Platform · บทเรียน 02

Schema ที่ดีเริ่มจากข้อเท็จจริง ไม่ใช่ช่องในหน้าจอ

วิธีแปลงกฎของธุรกิจให้เป็น table, column และ constraint พร้อมแนวทางเปลี่ยนโครงสร้างในอนาคตโดยรักษาข้อมูลเดิม

หลักเดียวที่ต้องจำ: schema คือกฎที่ฐานข้อมูลบังคับใช้ แม้โค้ดส่วนอื่นเขียนผิด ข้อมูลก็ไม่ควรหลุดออกจากกฎสำคัญ

ขั้นตอนออกแบบ

ถาม 4 คำถามก่อนเขียนโค้ด

1

ระบบต้องจำ “สิ่ง” อะไร?

สิ่งที่มีตัวตนและอายุของตัวเองมักเป็น table เช่น organization, user, team และ device

2

แต่ละสิ่งมีข้อเท็จจริงอะไร?

ข้อเท็จจริงที่เป็นค่าเดี่ยวมักเป็น column เช่นชื่อทีม, email, platform และสถานะอุปกรณ์

3

สิ่งเหล่านั้นสัมพันธ์กันอย่างไร?

หนึ่งองค์กรมีหลายทีม; ผู้ใช้เข้าร่วมหลายองค์กรได้ จึงต้องมี table ตัวเชื่อมสำหรับ membership

4

กฎอะไรห้ามผิด?

กำหนด primary key, foreign key, unique, not null, enum และ index ให้ตรงกับกฎธุรกิจ

คุณภาพของ schema

รายการตรวจสอบก่อนเพิ่ม table

  • table นี้แทนสิ่งหรือเหตุการณ์ที่มีความหมายจริง ไม่ได้สร้างตามหน้าจอเดียว
  • มี UUID primary key และ timestamp ที่จำเป็น
  • ถ้าเป็นข้อมูล tenant มี organization_id และ foreign key ที่ถูกต้อง
  • ค่าที่ต้องไม่ซ้ำมี unique constraint เช่น email หรือ slug
  • ค่าที่ห้ามขาดใช้ notNull; ค่าที่ไม่ทราบจริง ๆ จึง nullable
  • มี index บน foreign key และเงื่อนไขที่ค้นหาบ่อย โดยไม่สร้าง index ทุก column
  • กำหนดพฤติกรรมเมื่อข้อมูลแม่ถูกลบ เช่น cascade, restrict หรือ set null
  • ไม่มีข้อมูลลับหรือข้อมูลติดตามเกินความจำเป็นด้าน privacy

workflow ปัจจุบัน

เปลี่ยน schema ในเครื่องพัฒนา

1 · อธิบายกฎเขียนว่าธุรกิจต้องการจำอะไรและห้ามอะไร
2 · แก้ TypeScriptแก้ packages/db/src/schema/index.ts
3 · ตรวจโค้ดรัน lint และ type-check
4 · Previewอ่าน diff/SQL และคำเตือนจาก Drizzle
5 · Pushยืนยันเมื่อเข้าใจผลกระทบ แล้วตรวจผ่าน Studio
bun run lint
bun run check-types
bun db:push
bun db:studio

db:push อ่าน schema TypeScript, ตรวจโครงสร้างฐานข้อมูลปัจจุบัน, คำนวณ SQL ที่ต่างกัน แล้วนำไปใช้โดยไม่สร้าง migration file

ระดับความเสี่ยง

การเปลี่ยนแต่ละชนิดไม่เท่ากัน

ค่อนข้างปลอดภัยเพิ่ม nullable column, เพิ่ม table ใหม่, เพิ่ม index โดยเข้าใจผลกระทบต่อเวลา
ต้องเตรียมข้อมูลเพิ่ม not-null column, เปลี่ยนชนิดข้อมูล, เปลี่ยน unique rule, เปลี่ยน foreign key
เสี่ยงข้อมูลหายลบ table/column, rename ผิดเป็น drop+add, ลดขนาด type, ลบ enum value

Expand → Migrate → Contract

ตัวอย่าง: เพิ่ม timezone ที่ห้ามว่าง

อย่าเพิ่ม notNull() ทันทีเมื่อมีข้อมูลเก่า เพราะ row เดิมยังไม่มีค่า ใช้การเปลี่ยนเป็นระยะ:

Expand: เพิ่ม timezone แบบ nullable แล้ว push
Migrate data: เติมค่าให้ row เดิม และอัปเดตแอปให้เขียนค่าใหม่
Verify: ตรวจว่าไม่มี row ใดเป็น null และแอปเวอร์ชันเก่าไม่ได้ใช้งานแล้ว
Contract: เปลี่ยน column เป็น notNull() แล้ว push อีกครั้ง
Rename ก็ใช้แนวคิดเดียวกัน: เพิ่มชื่อใหม่ → copy/dual-write → เปลี่ยนการอ่าน → ตรวจ → ค่อยลบชื่อเก่า

ก่อน production
